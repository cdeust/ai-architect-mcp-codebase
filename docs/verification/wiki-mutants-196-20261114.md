# Scoped mutation run on the wiki skeleton export (#196, criterion 8)

Date: 2026-11-14. Tool: `cargo-mutants` 27.1.0, Rust 1.95.0, base `7c71c86` (main after #538).

## Scope

Every non-test source file the #196 pull requests changed (#506, #517, #519, #520, #522,
#529, #537, #538): `src/wiki/{checks,error,skeleton,communities,processes,coverage,missed,god_nodes,export,mod}.rs`,
`src/wiki_handlers.rs`, `src/tool_schemas_wiki.rs`. The one-line registrations #538 added to
`src/main.rs` (dispatch), `src/tool_schemas.rs` and `src/tool_profile.rs` are not in the run:
those files hold the other tools, and the registrations are exercised by the stdio test
`tests/wiki_export_stdio_196.rs`.

## Commands

```bash
export LBUG_BUILD_FROM_SOURCE=1 ZSTD_SYS_USE_PKG_CONFIG=1
# library files: their tests live in the library's test binary
cargo mutants --in-place --timeout 180 -C --locked -C --lib \
  -f src/wiki/checks.rs -f src/wiki/error.rs -f src/wiki/skeleton.rs -f src/wiki/communities.rs \
  -f src/wiki/processes.rs -f src/wiki/coverage.rs -f src/wiki/missed.rs -f src/wiki/god_nodes.rs \
  -f src/wiki/export.rs -f src/wiki/mod.rs -- -- wiki
# binary-side files: the tool handler is compiled into the server binary
cargo mutants --in-place --timeout 600 -C --locked -C --lib -C --bin=ai-architect-mcp-codebase \
  -f src/wiki_handlers.rs -f src/tool_schemas_wiki.rs
```

| `processes.rs:183` `\|\|` → `&&` in `read_edges` | `a_module_sharing_a_function_id_adds_no_edge_to_the_process` |

The last two were first recorded here as equivalent, on the assumption that a node id names
one label. It does not: `indexer::persist::nodes` keeps a field and a method sharing one id
(`TaskSet::len`), and a module and a function sharing one (`mod foo` and `fn foo`). Under
either mutant, a table with one end outside the clustered or participation labels (here
`HasField_Struct_Field`, `Defines_Module_Function`) yields a row whose other end carries the
id of a symbol on the page, and the edge is kept (review 1 of #539).

Three are equivalent: no input the schema can store gives a different output. None of the
three reasons assumes that an id names one label.

| Mutant | Why it is equivalent |
|---|---|
| `communities.rs:80` `&&` → `\|\|` in `membership_tables` | In `graph_store::REL_TABLES` (107 tables), a table starts with `MemberOf_` exactly when its target is `Community`, so both conditions select the same set. Checked by parsing the registry. |
| `missed.rs:113` `\|\|` → `&&` in `site_definers` | It adds the `Defines_*` tables whose target is not `CallSite` (the only tables into `CallSite` are `Defines_*`, checked in the registry); the query pattern binds the target node as `CallSite`, and a row of such a table ends at a node of another label, whatever its id, so those tables give no row. |
| `missed.rs:124` `\|\|` → `&&` in `site_definers` | Every row's site comes from the same `is_resolved = false` read as `open_sites`, which keeps every non-empty id, so `!sites.contains_key` only holds for an empty site id. Under the mutant, an empty-id site or an empty-id definer could enter the map, but attribution looks up page members and iterates `sites` (`attribute_missed`); an empty id is neither a valid member id nor a key of `sites`. |

An earlier run that passed only `-- --lib wiki` to every file reported the 14 binary-side

superseded by the binary-side run above and is not counted.
